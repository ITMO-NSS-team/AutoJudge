Да, план именно для **адаптации генерации судей под Jev 1.14**. Первый результат должен быть таким: MetaAgent остаётся LLM, создаёт задания для decision-моделей, а Jev выполняет проверки и формирует итоговое решение.

Я бы реализовал это следующим образом.

**1. За основу берём ядро из `main`**

Сохраняем существующий процесс:

```text
Трасса → MetaAgent → специализированные судьи → агрегатор → вердикт
```

Используем существующие `PoolGenerator`, построение параллельного графа и `Pipeline`. Из `iclr` имеет смысл перенести отдельные полезные изменения: исправление настройки температуры, явное задание модели судей и возможность тестировать без реальных API-вызовов. Весь экспериментальный код переносить не требуется.

Первую версию делаем для **полной трассы без инструментов и БД**, на примере Who&When. Это ограничивает объём первой реализации, но сохраняет главное в задаче — автоматическое создание специализированных судей.

**2. Меняем то, что генерирует MetaAgent**

Сейчас он возвращает примерно:

```json
{
  "name": "TOOL_USAGE_JUDGE",
  "instructions": "Проверь использование инструментов и объясни ошибки"
}
```

Для Jev нужно генерировать **роль, вопросы и критерии выбора ответов**. Например:

```text
Роль: проверка использования инструментов.

Вопрос 1:
Насколько корректно использовались инструменты?
Варианты: корректно / частично корректно / некорректно.
Для каждого варианта — описание критерия.

Вопрос 2:
Какой агент допустил решающую ошибку в этой области?
Варианты: агенты из трассы / ошибка не обнаружена.

Вопрос 3:
На каком шаге произошла эта ошибка?
Варианты: шаги из трассы / ошибка не обнаружена.
```

**MetaAgent придумывает специализацию и формулировки проверок. Список существующих агентов и шагов подставляет код из трассы.** Это предотвращает появление выдуманных идентификаторов.

Начнём с `choice`: его достаточно для первого рабочего варианта. Шаг ошибки — выбор конкретного шага, поэтому представлять его числовой оценкой `score` не нужно.

**3. Добавляем отдельный вызов Jev**

Текущие узлы обращаются к chat-моделям. Для Jev добавляем небольшой клиент на уже имеющемся `httpx`:

```text
model: typesafe/jev-1.14
state: задача и трасса
questions: вопросы, созданные MetaAgent
```

Запрос направляется в OpenRouter Decisions API. Он имеет собственный формат запросов и ответов, поэтому смены строки модели в текущем chat-клиенте недостаточно. [Документация API](https://openrouter.ai/docs/api/api-reference/alphadecisions/submit-a-decisions-request).

Результат узла сохраняем как выбранные ответы, вероятности, сведения о модели, стоимость и время запроса. В `Pipeline` добавляем возможность исполнять такой узел рядом с существующим LLM-узлом.

Модель исполнителя задаём в конфигурации: **MetaAgent не должен случайно выбрать другую модель вместо Jev 1.14.**

**4. Агрегатор тоже делаем на Jev**

Для первого варианта я бы трактовал «судьи — decision-модели» как требование заменить **всех судей, включая агрегатора**.

Агрегатор получает:

- исходную трассу;
- роли и вопросы промежуточных судей;
- их ответы и вероятности.

Затем выбирает итогового ответственного агента и шаг ошибки. Его собственные вопросы сначала зададим фиксированным шаблоном — так проще проверить работоспособность всей цепочки.

Отдельно меняем контракт результата: Jev не пишет свободное объяснение, поэтому обязательное текстовое поле `reason` придётся убрать или сделать необязательным в этом режиме. Вместо него сохраняем проверяемые данные: решения судей, вероятности и выбранный шаг. [Ограничения Jev](https://openrouter.ai/docs/guides/community/jev).

**5. Проверяем первую версию**

Сначала тестируем на сохранённых примерах ответов API:

- корректность сгенерированных вопросов;
- соответствие вариантов реальным агентам и шагам;
- разбор ответа Jev;
- передачу результатов агрегатору;
- обработку ошибок API.

Затем небольшой реальный прогон на нескольких трассах Who&When, после него — сравнение с исходным AutoJudge на одинаковом наборе. Проверяем точность определения агента и шага, стоимость, задержку и долю неудачных запусков. Стоимость считаем вместе с MetaAgent.

**Докручивать после работающей версии я бы стал в таком порядке:**

| Улучшение | Зачем |
|---|---|
| Формулировки вопросов и критериев | Проверить, понимает ли Jev именно причинную ошибку, а не просто заметный сбой |
| Агрегация вероятностей обычным кодом | Проверить, нужен ли дополнительный вызов Jev-агрегатора |
| Несколько вопросов в одном запросе | API это допускает; нужно измерить влияние на стоимость, скорость и качество |
| Переиспользование созданного пула | Сократить число вызовов MetaAgent на похожих трассах |
| Другие бенчмарки и длинные трассы | Проверить переносимость подхода и затем добавить подготовку контекста |

**Граница первой реализации:** одна команда запуска получает трассу Who&When, LLM автоматически создаёт специализированные decision-проверки, Jev 1.14 выполняет их и агрегацию, программа сохраняет итог и все промежуточные ответы. Это уже конкретное выполнение таски, на котором можно обоснованно выбирать дальнейшие улучшения.
