# План интерфейса AutoJudge

## 1. Цель

Собрать интерфейс для проверки агентной трассы специализированным пулом LLM-судей. Пользователь должен пройти путь от просмотра сгенерированных ролей до запуска оценки, изучения доказательств и принятия итогового вердикта.

План основан на двух PNG-макетах из корня проекта:

- `643488119-b5a99a0a-7738-4dc0-845c-03c54681823a.png` — экран готового пула судей;
- `643484283-d0b107fb-097d-43f2-9888-8ee46a8aaa39.png` — рабочее пространство оценки и результат.

## 2. Основной пользовательский сценарий

1. Система получает трассу, таксономию и схему результата.
2. Система генерирует четыре специализированные роли судей.
3. Пользователь просматривает роли и их проверки.
4. Пользователь подтверждает пул кнопкой **Use this pool**.
5. Открывается рабочее пространство оценки со статусом **Ready**.
6. Пользователь запускает оценку кнопкой **Run evaluation**.
7. Судьи выполняются независимо, после чего агрегатор формирует итог.
8. Пользователь изучает вердикт, виновного агента, шаг, уверенность, доказательства и стоимость запуска.

## 3. Информационная архитектура

### 3.1. Общая верхняя панель

- логотип и название AutoJudge;
- контекст: тип задачи и номер трассы;
- статус текущего этапа: `Generating`, `Generated`, `Ready`, `Running`, `Completed`, `Failed`;
- основное действие справа: **Use this pool**, **Run evaluation**, **Stop** или **Run again**.

Панель должна оставаться видимой при вертикальной прокрутке.

### 3.2. Экран «Сгенерированный пул судей»

#### Заголовочная область

- заголовок **Judge Pool Generated**;
- пояснение об источниках генерации;
- три метки контекста: трасса, таксономия, выходная схема.

#### Сетка ролей

Четыре карточки в сетке 2 × 2:

1. **Evidence Grounding** — проверка подтверждения утверждений источниками;
2. **Causal Attribution** — поиск ответственного агента и причинного шага;
3. **Tool-Use Compliance** — проверка корректности инструментальных вызовов;
4. **Logical Consistency** — поиск противоречий и неподтверждённых выводов.

Каждая карточка содержит:

- цветовой идентификатор и иконку;
- название роли;
- метку `Auto-generated`;
- краткую цель;
- список конкретных проверок;
- действие **View instructions** или открытие карточки для просмотра полного промпта.

#### Сводка генерации

Правая панель содержит:

- количество судей;
- область действия пула: для одной трассы или переиспользуемый;
- наличие размеченных примеров;
- схему передачи результатов судей агрегатору.

#### Нижнее уведомление

Информационный блок напоминает проверить роли перед запуском. Кнопка открывает инструкции всех судей в боковой панели или модальном окне.

### 3.3. Экран «Рабочее пространство оценки»

Экран делится на три колонки.

#### Левая колонка — Trace & Configuration

- поиск по шагам трассы;
- вертикальная временная шкала шагов;
- для каждого шага: номер, агент и использованный инструмент;
- выделение выбранного шага;
- раскрытие полного входа, выхода и вызовов шага;
- селекторы таксономии и выходной схемы;
- выбор режима: **Full trace** или **Summary + Retrieval**.

При выборе доказательства справа соответствующий шаг должен автоматически выделяться и прокручиваться в видимую область.

#### Центральная колонка — Generated Judge Pool

- карточки четырёх судей со статусами;
- краткое описание ответственности;
- компактный вывод каждого судьи;
- визуальная связь с агрегатором;
- карточка агрегатора с итоговым статусом синтеза.

Статусы карточки: `Queued`, `Running`, `Complete`, `Warning`, `Failed`. Во время выполнения карточка показывает индикатор прогресса; при ошибке — краткую причину и кнопку повтора только этого судьи.

#### Правая колонка — Final Verdict

- крупный тип вердикта и его severity-цвет;
- виновный агент;
- связанный шаг;
- confidence в диапазоне 0–1;
- доказательства с цитатами и источниками;
- объяснение связи между доказательствами и вердиктом;
- метрики запуска: время, число LLM-вызовов, стоимость.

Каждое доказательство должно открывать исходный шаг без потери текущего результата.

## 4. Компоненты

| Компонент | Назначение | Ключевые варианты |
|---|---|---|
| `AppHeader` | Контекст, статус, главное действие | Generated, Ready, Running, Completed, Failed |
| `ContextChip` | Трасса, таксономия, схема | icon + label |
| `JudgeCard` | Роль, описание, проверки и результат | generated, queued, running, complete, warning, failed |
| `GenerationSummary` | Параметры и схема пула | compact, expanded |
| `TraceTimeline` | Навигация по шагам | default, selected, evidence-linked, error |
| `ConfigPanel` | Таксономия, схема и режим | editable, locked during run |
| `AggregatorCard` | Состояние синтеза | queued, running, complete, failed |
| `VerdictBanner` | Тип итогового решения | success, warning, error, neutral |
| `EvidenceCard` | Цитата и источник | internal step, external source |
| `RunMetrics` | Время, вызовы и стоимость | estimated, live, final |

## 5. Состояния и поведение

### До запуска

- основное действие недоступно, пока трасса, таксономия и схема невалидны;
- конфигурацию можно менять;
- изменение конфигурации после генерации помечает пул как устаревший и требует регенерации.

### Во время запуска

- конфигурация блокируется;
- отображается общий прогресс и статус каждого судьи;
- частичные результаты появляются по мере готовности;
- итоговый вердикт формируется только после завершения обязательных судей;
- остановка требует подтверждения, если уже потрачены LLM-вызовы.

### После запуска

- доступны все доказательства и переходы к шагам;
- можно повторить весь запуск либо отдельного упавшего судью;
- результат можно экспортировать в JSON по выбранной выходной схеме;
- при изменении входных данных текущий результат сохраняется как предыдущий запуск.

### Ошибки и пустые состояния

- трасса не загрузилась;
- в трассе нет шагов;
- пул не удалось сгенерировать;
- отдельный судья завершился с ошибкой;
- агрегатор не может сформировать вердикт;
- доказательство ссылается на отсутствующий шаг;
- стоимость или usage недоступны.

В каждом случае интерфейс показывает причину, сохранённые результаты и одно конкретное действие восстановления.

## 6. Визуальные правила

- фон — белый или очень светлый холодный серый;
- основной текст — тёмно-синий почти чёрный;
- основной action — насыщенный синий;
- роли имеют постоянные цвета: синий, фиолетовый, бирюзовый, оранжевый;
- зелёный используется только для успешного состояния;
- красный — только для ошибки или отрицательного вердикта;
- карточки имеют тонкую границу, небольшой радиус и минимальную тень;
- цвет всегда дублируется иконкой и текстом статуса.

Для единообразия следует выбрать одну иконку для **Logical Consistency**: на двух макетах используются разные символы.

## 7. Адаптивность

### Ширина от 1280 px

- три колонки на рабочем экране;
- правая сводка на экране пула;
- сетка судей 2 × 2.

### Ширина 768–1279 px

- левая конфигурация становится выдвижной панелью;
- результат остаётся рядом с пулом либо открывается вкладкой;
- карточки судей сохраняют две колонки при достаточной ширине.

### Ширина до 767 px

- один столбец;
- переключатель разделов: `Trace`, `Judges`, `Verdict`;
- фиксированная нижняя панель главного действия;
- схема агрегатора заменяется компактным текстовым статусом.

## 8. Доступность

- управление всеми элементами с клавиатуры;
- видимый `focus` у кнопок, карточек и шагов;
- семантические заголовки и landmarks;
- `aria-live` для смены статусов запуска;
- контраст текста и controls не ниже WCAG AA;
- tooltips не являются единственным источником информации;
- анимации прогресса учитывают `prefers-reduced-motion`.

## 9. Порядок реализации

### Этап 1 — каркас и демо-данные

- общая верхняя панель;
- оба экрана и переход между ними;
- сетка судей, трасса и статичный итоговый вердикт;
- desktop layout по макетам.

### Этап 2 — состояния запуска

- модель статусов;
- прогресс судей и агрегатора;
- loading, empty и error states;
- блокировка конфигурации во время запуска.

### Этап 3 — исследование результата

- связь доказательств с шагами трассы;
- просмотр полных инструкций судей;
- раскрытие данных шага;
- экспорт результата в JSON.

### Этап 4 — качество

- адаптивные layouts;
- клавиатурная навигация и screen reader labels;
- визуальные и компонентные тесты;
- проверка длинных названий, больших трасс и частичных ошибок.

## 10. Критерии готовности MVP

- пользователь видит, из каких четырёх ролей состоит пул и что каждая проверяет;
- пул можно подтвердить и перейти к рабочему экрану без потери контекста;
- запуск отражает отдельный статус каждого судьи и агрегатора;
- итог содержит вердикт, агента, шаг, confidence, доказательства и объяснение;
- переход из доказательства выделяет соответствующий шаг трассы;
- ошибки отдельных судей не скрывают уже полученные результаты;
- интерфейс работает с клавиатуры и остаётся читаемым на ширине 768 px;
- основные состояния покрыты тестами: generated, ready, running, completed и failed.

## 11. Открытые продуктовые решения

1. Можно ли редактировать автоматически сгенерированные инструкции судей или только просматривать их?
2. Допускается ли итог при частичной ошибке одного из судей?
3. Нужно ли сохранять историю запусков и сравнивать вердикты?
4. Является ли пул строго одноразовым для трассы или его можно сохранять как шаблон?
5. Какие типы итогового вердикта и уровни severity определены выходной схемой?
