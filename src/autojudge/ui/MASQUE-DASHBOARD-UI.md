# UI MASQUE Dashboard

## 1. Назначение

MASQUE Dashboard — одностраничный Streamlit-интерфейс для диагностики трасс мультиагентных систем. Пользователь загружает собственную трассу или выбирает демонстрационный пример, запускает диагностический pipeline и получает сводный отчёт с типами ошибок, проблемными агентами, проверкой доказательств и детализацией по шагам.

Описание основано на проверке исходного кода и локально запущенного интерфейса проекта `masque-dashboard`.

## 2. Основной пользовательский сценарий

1. Выбрать источник трассы: **Own Trace** или **Example Trace**.
2. Загрузить JSON/CSV либо выбрать набор данных и номер примера.
3. При необходимости открыть **Advanced Options**.
4. Для собственной трассы указать OpenRouter API key.
5. Опционально указать ground truth.
6. Нажать **Analyze Trace**.
7. Наблюдать выполнение пяти этапов pipeline.
8. Изучить сводные статусы, диаграммы, timeline и детали findings.
9. Скачать полный отчёт в JSON.

## 3. Состояния интерфейса

### 3.1. Начальное состояние

Левая панель содержит все элементы ввода, а основная область показывает:

- цель интерфейса;
- четыре шага запуска;
- пример минимального message-list JSON;
- пояснение об ограничениях raw framework exports;
- перечень данных, которые появятся после анализа.

### 3.2. Выполнение анализа

В sidebar появляется блок **Pipeline Progress** с пятью этапами:

1. Normalize trace;
2. Run LLM judges;
3. Run deterministic validators;
4. Verify evidence;
5. Build report.

После завершения показывается время выполнения. Ошибки pipeline выводятся над отчётом; частично сформированный отчёт может оставаться доступным.

### 3.3. Готовый отчёт

Основная область заменяется диагностическим отчётом:

- заголовок и Trace ID;
- кнопка скачивания JSON;
- четыре сводные карточки;
- диаграммы типов ошибок и проблемных агентов;
- вкладка проверки доказательств;
- timeline трассы;
- постраничная панель Finding Details.

## 4. Информационная архитектура

### 4.1. Sidebar — ввод и состояние pipeline

#### Брендинг

- логотип MASQUE;
- название **Multi-Agent System Diagnostic Platform**.

#### Input Trace

- сегментированный переключатель **Own Trace / Example Trace**;
- загрузчик JSON/CSV для собственной трассы;
- выбор набора данных и номера трассы для примера;
- popover **Advanced Options**;
- поле OpenRouter API Key;
- опциональное поле Ground Truth;
- основная кнопка **Analyze Trace**.

#### Pipeline Progress

- номер этапа интерфейса;
- общий статус анализа;
- список пяти шагов pipeline;
- итоговое время.

### 4.2. Верхняя часть отчёта

#### Заголовок

- **Diagnostic Report**;
- Trace ID;
- кнопка **Download Report (JSON)**.

#### Сводные карточки

| Карточка | Содержимое | Варианты |
|---|---|---|
| Final Answer | Корректность финального ответа | Correct, Incorrect, Unknown |
| Diagnostic Status | Наличие диагностических проблем | Issues Found, No Issues, Unknown |
| Human Review | Необходимость ручной проверки | Required, Not Required, Unknown |
| Issues by Severity | Количество findings по уровням | Critical, Major, Minor |

Цвет и иконка дублируют состояние: зелёный — успех, оранжевый — предупреждение, красный — ошибка, серый — неизвестно.

### 4.3. Аналитические диаграммы

Левая панель использует вкладки:

- **Top Failure Types** — donut chart с распределением findings по метрикам;
- **Evidence Verification** — donut chart со статусами Verified, Weak и Invalid.

Правая панель:

- **Culprit Agents** — горизонтальная bar chart;
- агенты отсортированы по количеству findings;
- цвет столбцов отражает относительную интенсивность значений.

### 4.4. Trace Timeline

Каждый элемент timeline содержит:

- номер шага;
- роль или агента;
- severity badge, если шаг связан с finding;
- сокращённый preview сообщения;
- управляющий символ раскрытия;
- полный текст после раскрытия.

Severity шага вычисляется по связанным findings. Если к одному шагу относятся findings разной тяжести, отображается максимальная тяжесть.

Для raw traces без нормализованной истории timeline скрывается и заменяется поясняющим пустым состоянием.

### 4.5. Finding Details

Панель показывает один finding за раз и содержит:

- severity;
- пагинацию между findings;
- metric;
- confidence;
- source;
- evidence status;
- описание проблемы;
- связанные доказательства и шаги;
- объяснение, почему это ошибка;
- рекомендуемое исправление.

Связь с timeline сейчас преимущественно визуальная: finding содержит номера шагов, а timeline подсвечивает severity связанных элементов.

## 7. Сильные стороны

- понятная последовательность **input → pipeline → report**;
- сводные KPI позволяют быстро оценить результат;
- findings связаны с конкретными агентами и шагами;
- severity используется последовательно в карточках, timeline и деталях;
- результат не исчезает при изменении текущего выбора в sidebar;
- можно скачать полный структурированный отчёт.

## 8. Ограничения текущего UI

- почти весь UI и его логика находятся в одном Python-файле примерно на 1900 строк;
- при длинной трассе timeline становится перегруженной и требует поиска, фильтров и виртуализации;
- отдельные LLM-судьи и их промежуточные результаты не показаны;
- связь timeline и Finding Details недостаточно интерактивна;
- нет отдельного экрана формирования или проверки judge pool;
- сложные пользовательские панели не имеют собственных responsive-breakpoints;
- одновременно используются нативные компоненты Streamlit и значительный объём хрупких CSS-селекторов;
- применены устаревающие Streamlit API `use_container_width` и `st.components.v1.html`.

## 9. Применение в AutoJudge

Из MASQUE Dashboard целесообразно перенести:

- пошаговую структуру запуска;
- компактные KPI над подробным отчётом;
- severity badges;
- диаграмму проблемных агентов;
- связку timeline и Finding Details;
- экспорт JSON.

В AutoJudge следует развить эту модель:

- добавить отдельный экран сгенерированного judge pool;
- показывать статус и результат каждого судьи;
- использовать трёхколоночный рабочий экран `Trace / Judges / Verdict`;
- сделать evidence-карточки кликабельными и синхронизировать их с timeline;
- добавить поиск, фильтрацию и виртуализацию длинных трасс;
- отделить успешность pipeline от содержательного вердикта;
- предусмотреть мобильную и планшетную компоновку.
